## 数据库存的是什么

所选快照 `query-c9e2d02426106321794973a3`，schema `research-query-v0.3`，共 37 条候选记录、52 个证据对象、4 份来源。候选行数不是独立事实数，也不是全文结构化程度。

| 来源 | 解析块 | 入库候选行 |
| --- | ---: | ---: |
| 2025 10-K | 999 | 6 |
| 2026 Q1 10-Q | 695 | 7 |
| 2026 Q2 10-Q | 825 | 11 |
| 2025 Q4 电话会 | 282 | 13 |

原始材料是冻结的 HTML/PDF；数据库是这些来源和抽取产物的可重建查询投影。四张物理表是 `observations`、`sources`、`evidence`、`metric_definitions`。页面 Schema 从数据库读取表名、字段、类型和可空性。数值使用 `DECIMAL(38,12)`；分母、语气、维度、原始抽取记录等保存在完整记录 `payload` 中。

页面主表逐行展示 `observations`，把数值与必要语义组合呈现；点击“处理过程”还可查看数据库物理列。它是只读核验界面，不提供任意 SQL 执行或数据编辑。

## 两条实际处理链

**财报收入**：原文表格单元格 `20,028` → XBRL 上下文确认 Google Cloud、2026 Q1、USD、scale=6 → 抽取记录 `20028000000 USD` → 入库保留相同数值，将声明过的 XBRL 分部维度映射成 `reporting_segment=google-cloud`。原数字、尺度、原维度和两处原表证据都保留。

**电话会比例**：原话 “just over half of our ML compute is expected to go towards the Cloud business” → 模型抽取 `value=50`，限定措辞仍在原文引用 → 经明确绑定来源的适配器，入库为 `value=50, relation=gt, unit=percent, denominator=total_ml_compute, modality=expected`。50 是阈值；不能当成精确预测，也不能把分母换成总 CapEx。

财务记录主要依靠确定性解析；电话会记录来自之前的 DeepSeek 抽取实验和来源限定适配器。上述结果不代表任意公司、任意表格或任意电话会均已泛化支持。

## 信息损耗：哪些已确认，哪些未评估

| 环节 | 已保留 | 查询层仍有的边界 |
| --- | --- | --- |
| 原文到文档索引 | 原文件、文本块、表格单元格、页码/定位 | 视觉布局与所有图片内容未证明完整转换为可查询字段；10-K 索引含 2 个图片块，不等于已做完整 OCR |
| 索引到抽取记录 | 所选指标/片段及原话引用 | 37 行只覆盖选定目标，未抽取内容仍需回读原文；没有全文召回率或总体损耗百分比 |
| 抽取到规范化 | 原记录、尺度、维度、关系、分母、语气 | “略高于”的接近程度只有原话，不能从单一数值字段还原 |
| 时间与版本 | 来源版本、公开日期、内容指纹 | 公开时间只有日期精度，不能支持严格盘中时点回测 |

原文仍保留表示可回溯，不表示查询层无损。下一步质量评估应分开衡量“抽取遗漏”“语义保真”和“来源可追溯”，不能用引用块数除以总块数充当召回率。

## 新数据现在如何更新

目前**没有自动增量同步**。真实路径是：

1. 人工或脚本获取并冻结新材料，记录来源身份、公开日期、文件与内容指纹。
2. 生成文档索引和候选抽取。超出现有公司、财年或措辞适配范围时，先增加映射与验证。
3. 准备显式 `DatasetBuildSpec`，列明要保留的历史输入及新增输入，并绑定来源、适配器和 hash。构建器不会读取旧数据库后自动补齐历史。
4. `build_dataset` 在新目录重建数据库、证据、schema 和 manifest。校验通过后才将临时目录变为目标目录；拒绝覆盖已有目标。构建输入、适配器等参与 snapshot 身份计算。
5. 核验新增、修订、重复和冲突，显式选择新快照供后续查询；页面展示另需登记明确的快照路径与 manifest hash。

旧查询的 `snapshot_id` 不变，不会悄悄切换新数据。同口径、同值重复披露保留各自来源，不能相加；支持范围内的取数冲突会标为歧义并阻止相关计算。当前没有自动选定“最新修订为真”的规则，新快照也不等于审核或采纳。

## 本轮验证与下一步

56 项聚焦测试通过，覆盖实际物理值与 payload 一致、文件指纹、公司隔离、来源文本转义、数值尺度、阈值语义、旧快照不可覆盖、重复/冲突处理和原有页面回归。新增两家公司独立小数据集验证，不以 Alphabet 一个例子代替边界检查。

离线更新测试使用已有冻结材料模拟“历史财务输入 → 历史财务输入加电话会输入”，24 行变为 37 行，产生不同 snapshot_id；历史记录包含在新快照中，旧快照文件逐字节不变且仍可打开。这证明显式重建行为，不证明自动发现、抓取新披露或任意修订处理已经完成。

建议下一步先做一个可审阅的更新批次：来源版本登记 → 新增/修订/重复/冲突差异 → 验证结果 → 显式发布候选快照。随后再增加自动发现和调度；直接定时覆盖数据库会破坏当前已建立的查询复现能力。该更新批次流程尚未在本轮实现。

## 整份 10-K 的业务与风险分析如何处理

“根据 FY2025 Google/Alphabet 10-K 分析重点业务和关键风险”属于文档分析；text2sql 是 Data Agent 的一个能力分支，不能覆盖完整任务。先绑定具体年报版本，区分 FY2025 年报与 2025 年提交的年报；只基于该年报的任务不能混入后来电话会或网页材料。

| 步骤 | Data Agent 提供 | Analysis Agent 负责 |
| --- | --- | --- |
| 来源与阅读计划 | 冻结来源、目录、章节范围 | 把重点业务/关键风险拆成证据需求 |
| 章节阅读 | 业务介绍、风险因素、MD&A、相关附注；分批完整读取列表/表格及其上下文 | 建立业务结构、收入模式、驱动因素与风险机制 |
| 交叉核验 | 按指定年报限定的数字/原文检索；每次带页码、block ID、来源版本 | 核查业务重要性，追问反例、限定和缺口 |
| 输出与覆盖 | 已读章节/块、未读范围、引用、取数记录 | 给出业务分析表、风险—影响路径表，区分公司披露与分析判断 |

现有 `DocumentReader` 已支持 `outline/search/read`，原有 `analysis_comparison.py` 也通过这些工具执行文档研究，因此不是从零开始。当前新 `DataQueryAgent` 只暴露 `query/read_context/finish/clarify`；文档检索是字面匹配、默认只取少量命中，尚未直接开放目录导航和系统章节阅读，也未验收全文业务/风险覆盖。

另一个实际缺口是来源限定：目前 `RecordRequest`/`CalculationRequest` 没有单份来源版本约束，取数 SQL 按实体、指标、期间、性质和 cutoff 筛选。对“只根据这份 10-K”的任务，不能直接把跨来源快照里的同期间数值当作合格证据。可先显式构建仅含该年报的快照；长期应在统一请求中增加来源版本范围，并贯穿 SQL、计算依赖和原文读取。

下一步文档分析接入建议：复用已有 reader，将目录发现与可续读章节接口接入 Data Agent；返回带来源和阅读覆盖的 evidence packet；Analysis Agent 综合并迭代取证。逐章节覆盖检查和结论证据检查需要单独验收，不能把“找到了几段文字”或 planner 的 `answered` 等同于“已完整分析”。本轮没有执行该年报的模型分析，也没有声称上述统一链路已经实现。

## 文本、表格、图片应如何统一返回

当前执行产物已经包含文本：`evidence.quote` 保存引用，`contexts[].blocks[].text` 保存完整读取块，记录的 `summary` 保存抽取陈述。查询返回的内容不限于数据库行。已有图片索引/定位不等于已将图片送入模型；当前自然语言查询模型接口传输 JSON 文本，没有接通 OCR 或图片理解。

设计上分开两件事：**工具决定如何获取和处理，产物类型决定如何表达和消费。** SQL 可以返回含文本的表；阅读文档可以返回文字、原始表格和图片；OCR 的输出是从图片派生的文字。因此不能用“SQL/文本/图片”作为互斥查询模式。

| 所需信息 | 可选执行能力 | 主要返回产物 |
| --- | --- | --- |
| 指标、期间对比、计算 | schema 发现、SQL、确定性计算 | 表格/标量，附单位、期间、关系、分母及原始依据 |
| 业务描述、风险条件、管理层解释 | 目录导航、章节续读、文本搜索 | 完整文本块、上下文、原话引用及阅读覆盖 |
| 图表、扫描表、插图 | 获取原始图片/页面区域，按需 OCR 或视觉理解 | 原图引用 + OCR 文本/提取表格/图表描述，派生产物与原图关联 |
| 本地缺少的公开材料 | 按来源政策搜索、获取、冻结、解析 | 新来源及其产物；未经获取验证的搜索摘要只作发现线索 |

建议统一返回一个“证据包”，它是任务相关产物的容器，而不是一份通用摘要：

1. **产物列表**：文字块、表格/标量、图片、派生提取、明确缺口，各有类型与 ID。图片优先保存受控资源引用、页码、区域和内容 hash，供支持视觉的消费者按需读取，不把二进制混进每次文字返回。
2. **共同来源信息**：公司、文档版本、公开日期、页码/块/区域、原始与派生关系、单位/限定等适用字段；同一证据在原文和 SQL 中被引用时关联同一来源。
3. **覆盖与续读信息**：搜索范围、已读章节、未读部分、未解析图片、下一批游标、失败/预算限制。`partial` 与“没有披露”不能混为一谈。
4. **执行记录**：实际使用的工具、SQL/参数、检索与读取动作、解析版本/模型及费用，支持回放和比对。

纯业务分析可以全部走文档读取；收入占比需同时读取业务描述与财务表；只有图中存在的关系才触发图片处理。任务计划可以包含多个子任务，各自选择能力；数据/来源变化只会让相应证据或派生产物失效，不应静默覆盖以前的研究。

Data Agent 负责取得、解析、规范化和说明证据局限。可以提供明确标注的提取或摘要，但必须区分原话、确定性转换与模型派生，保留回读依据；业务重要性、风险优先级及综合结论由 Analysis Agent 判断。当前已具备表格/文本基础，统一多模态证据包、章节覆盖管理、OCR/视觉和自动扩源仍属待实现能力。
