## 1. 结论

本轮支持继续保留 Uteki 的原始文档索引与阅读器，优先完善财务上下文、类型化记录和证据关联。没有发现需要整体替换 parser 的依据，也没有实际运行 Claude/GPT 对照。

已经验证的收益是：

- 原有六个 Cloud 年度数值全部保持一致，现在每项具有明确日期、主体维度、单位/scale、表头和原单元格定位。
- Q1/Q2 材料新增 18 条可查询记录，能区分单季、累计和时点，支持有操作数来源的单季现金支出计算。
- 电话会管理层指引保留原话、说话人和适用期间；一个真实的跨段限定说明被关联到对应指引。
- 缺少某个指标、材料尚未披露、来源 hash 不一致，都明确返回缺失或拒绝，不让下游自动补齐。

同时发现一项代价：在保留相同原文证据的前提下直接叠加完整结构化 JSON，两组消费输入分别增加 **38.1% 和 96.5% 字符**。尚不能声称节省 token/费用或提高最终回答质量。后续应测量收益后，再决定默认数据包应保留多少字段和语境。

## 3. 最值得看的三个具体变化

### 3.1 数字正确还不够，必须说明它属于什么期间

Google Cloud 的原有 FY2025 收入为 **58,705 USD millions**，本轮仍为相同数值，没有人为制造变化。新记录额外绑定 2025-01-01 至 2025-12-31、Cloud 分部、财务 concept、USD、scale 6、显示原文与单元格/表头。

在 2026 Q2 季报中，同一 Cloud 收入指标则有：

| 期间 | 收入（USD millions） | 营业利润（USD millions） |
| --- | ---: | ---: |
| 2025 Q2 单季 | 13,624 | 2,826 |
| 2026 Q2 单季 | 24,768 | 8,814 |
| 2025 H1 累计 | 25,884 | 5,003 |
| 2026 H1 累计 | 44,796 | 15,412 |

仅保存“2026 + revenue”不足以区分后两种 2026 期间。新记录使用精确起止时间和 period kind；Q1 同时标明其时间范围也可作 YTD 使用，避免人为复制成两个不同经济事实。

另外保存两个 Cloud RPO 时点余额：2026-03-31 为 462,300、2026-06-30 为 513,900 USD millions。它们是履约义务余额，不能当作相应季度已确认营收。

### 3.2 计算值与原文披露值分开

本轮 Capex 的明确财务定义为 `PaymentsToAcquirePropertyPlantAndEquipment`，即购买物业、厂房和设备的现金支出金额。原文现金流表的括号表示流出，XBRL 指标数值本身为正；解析器不再依赖显示括号一概取负。

| 派生期间 | 公式（USD millions） | 派生值 |
| --- | --- | ---: |
| 2025 Q2 | H1 39,643 − Q1 17,197 | 22,446 |
| 2026 Q2 | H1 80,598 − Q1 35,674 | 44,924 |

每项计算保存公式版本和两个操作数的 record IDs。主体、币种、维度、指标、会计口径或期间不匹配时拒绝计算。这里的企业现金支出不自动等于管理层采用的所有 CapEx 定义，也不代表 Cloud 分部资本开支。

### 3.3 原话已存在，关联仍可能缺失

CFO 的 FY2026 CapEx 指引为 **USD 175–185 billion**。指引所在 block 151 包含全年期间和投资逐步增加的说法，block 153 则指出供应、组件定价和现金支付时间可能造成金额变化。

Step 3 已保存 block 153 的独立管理层陈述，但通过 Guidance 读取时只有 block 151。Step 4 在同一 speaker/turn 内建立受限上下文关联，使指引带上 151–153 三段及具体条件引用。

这次收益是“查询指引时能拿到其限定”，并非新发现了原文中不存在的信息。QA-06 仍完整保留问题、回答与追问，分析师提问不会变成公司事实；“Cloud 获分配超过一半 ML compute”也没有被转换成“Cloud 占全公司 CapEx 超过一半”。

## 4. 负结果、失败和修正

### 输入体积增加

| 消费问题 | 原文输入字符 | 原文＋完整结构化记录 | 变化 |
| --- | ---: | ---: | ---: |
| A1：Cloud 单季经营与累计数区分 | 24,943 | 34,443 | +38.1% |
| A2：CapEx 指引、限定与配置含义 | 10,574 | 20,775 | +96.5% |

以上是 candidate-04 准备阶段的字符量，双方原文 blocks 完全相同。后续发现双方都漏了表前单位说明，已在 candidate-05 补齐。真实调用测得 A1 输入 token 10,038→13,203、A2 4,153→7,404；结果及失败另见最新报告，不能将字符量当作 token。

因此暂不把“所有中间 JSON 原样塞给 Agent”设为默认生产输入。需完成消费验证，再单独实验字段投影和按需展开证据，避免同时改变多项因素。

### 局部补读曾带入无关内容

初次 Step 4 将 CEO 指引后面的 AI 议程和概述也带入。该尝试保留在 [初次结果](../experiments/research_data_quality/2026-09-22-execution/step-04/output.json)。增加明确的话题边界后，CEO 仍保持 1 段；CFO 的限定关联保留。没有把“读得更多”直接算成改善。

### 实验准备过程的一次失败

第二个候选在准备模型输入时，错误假定所有文档的根节点 ID 都叫 `document`；SEC 索引使用带版本的节点 ID。已改为按 `kind=document` 查找真实节点，并加入可重放的准备测试。见 [保留的失败记录](../experiments/research_data_quality/2026-09-22-candidate-02/failure.json)。这属于实验适配器错误，不是财报内容解析错误。

### Q4 发布稿来源不一致

本地原文 hash 与来源清单/索引声明不匹配，该材料继续排除。未改写来源或只修改 hash 让它通过。详细指纹在 [Step 0 记录](../experiments/research_data_quality/2026-09-22-step-00/README.zh-CN.md)。其余四份来源满足本次指纹检查；这不代替人工语义审核。

## 5. 验证范围与结论边界

- 本轮 **51 项相关测试通过**；最后调整评价检查后，相关 **16 项再次通过**。覆盖已有读取/Cloud/研究数据回归及新增期间、单位、表头、rowspan、来源一致性、查询缺口、时点、计算、归属、Q&A 和指引上下文检查。
- 预先登记的 **24/24 条数值目标**在主体、指标、起止/时点、币种、报告口径和数值上匹配。参考来自实施前的原文阅读，由执行 Agent 整理，**不是独立人工 Gold 或盲测准确率**。
- 24 条记录保留 **33 个原文披露 occurrence**。重复披露不计为独立证据票数；本次范围内未报告数值冲突或解析诊断，不代表全篇/所有 taxonomy 均覆盖。
- 同一公司 Q1 材料验证了代码不依赖 Q2 的具体表格 ID，但仍不能证明跨公司或未见材料的泛化能力。
- 电话会仅对显式 CapEx 数值范围和关键词命中的 Cloud/CapEx 陈述建立候选。未知表达、定性指引的全面分类、复杂指代和全文遗漏率仍未完成独立评估。
- 原始源、原索引、旧研究快照和人工采纳记录均未修改。本次新增代码通过实验入口使用，尚未接入现有产品的默认研究执行路径。
