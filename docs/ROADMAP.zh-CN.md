# Uteki 产品路线图与版本治理

- 编制日期：2026-09-18。
- 状态：工作提案；下一版范围供共同评审，远期方向随证据修订。此文件不代表任何研究结果、Gold 或版本已被验收。
- 当前能力里程碑仍是 [M0](M0_SCOPE.zh-CN.md)。建议产品版本从 v0.2 开始承接它，不改变现有 package、数据、索引、benchmark 的版本号。
- 下一版详见 [v0.2 执行计划](releases/V0_2_PLAN.zh-CN.md)，各版使用 [验收记录模板](releases/ACCEPTANCE_TEMPLATE.zh-CN.md)。
- 目标职责与产品方向见 [Agent 职责与投资闭环提案](AGENT_SYSTEM_DESIGN.zh-CN.md)：六类业务职责，分析领域独立评测，长期多头与偏满仓可配置，阅读、研究采纳和交易授权分别记录。
- Analysis 的持续 Watch → Review → Update 与团队协作属于核心设计要求；每个版本按下表交付可验证能力，不将设计方向记作已经实现。

## 1. 长期目标

建立一个服务长期多头价值投资的系统：发现值得研究的公司，解释生意、形成有证据的投资假设、复算财务与估值、持续识别判断变化，并将研究建议连接到有约束的资本配置、风险检查与获授权的交易执行，保留每次决定的依据。

长期维护的核心成果是一份版本化的公司投资案例：

> 事实与证据 → 经营假设 → 财务预测 → 估值情景 → 价格与预期差 → 风险与重审条件 → 人工决定及复盘。

报告是案例的阅读形式。事实、假设、计算和人的决定分别记录。每一项重要判断均能追溯到当时可用的信息，能够说明什么新证据会改变它。

Analysis 持续维护案例、跟踪计划和待验证问题：Watch 识别新输入及到期复核，Review 检验原假设并安排领域工作，Update 形成有依据的修订或无变化结论。共享研究状态、版本化任务交接和团队复核从领域契约阶段就设计，不能在单次报告流程定型后再补。

公司挖掘产生候选、发现依据与待验证问题，复用 Data 的来源和查询能力。研究之后的目标链路是：投资案例与建议 → 账户目标组合与资金计划 → 独立风险检查 → 有效授权范围 → 订单、成交与对账。长期偏向充分投资，通过目标投资比例、现金缓冲和约束配置实现；无法满足约束时明确返回冲突。候选入选、研究采纳和订单授权分别记录。

## 2. 工作原则

**做对的事情：每版解决一个真实研究问题。** 每个 todo 必须说明谁会使用、改善哪个研究环节、如何观察改善。功能数量、Agent 数量和报告篇幅不作为版本目标。

**把事情做对：每项完成都有可检查的产物。** 来源、口径、版本、计算、异常、成本和人工结论进入验收记录。代码完成、工程验证、研究验证分别记录。

执行规则：

1. 同时只有一个活跃的能力里程碑。后续版本先保留方向与关键任务，在进入前一版验收时再细化。
2. 先由人跑通有价值的研究流程，再自动化其中已明确的步骤。
3. 软件行为、研究质量、投资结果分别评估。测试通过不能替代研究验收，短期股价表现也不能单独证明研究判断正确。
4. 保持模块化单体。架构调整由当前任务的重复、耦合或错误驱动，限定在可验收范围内。
5. 资料获取、来源时点、版本管理、预算、运行记录、必要的恢复能力贯穿每版；多人权限与运营能力按真实协作需求增加。
6. 每次实验先写假设和预算，再执行；保留失败与负结果。研究者保留最终判断。

## 4. 大版本方向

以下是产品能力版本建议，不是交付日期承诺。各版本以验收结果决定是否进入下一阶段。

| 版本 | 核心研究问题与交付结果 | 主要 todo | Milestone 与验收依据 |
| --- | --- | --- | --- |
| **v0.2 可复现研究基线**，建议下一版 | 给定一份 Alphabet 年报，能否得到可审核的业务地图，并准确知道自动化哪里薄弱？ | 固定完整来源；处理证据异常；试用并冻结 G0；人工 Gold；最简 baseline；业务地图评分与逐错分析；一次单因素实验 | **R2-A** 来源与契约（G0）；**R2-B** 人工 Gold（G1）；**R2-C** 基线、评测及实验（G2–G4）。冻结产物能独立重放，质量与限制如实报告 |
| **v0.3 可复算的财务与经营基线** | 这家公司历史上如何创造现金、使用资本？ | 同一公司多年度及季度数据；指标/数据点身份；币种单位、口径与重述；正常化调整；经营驱动与财务关系；持久化研究状态与财务任务输入输出；人工维护投资问题及跟踪对象 | **R3-A** 时点、口径与版本化研究状态；**R3-B** 历史财务模型及任务契约；**R3-C** 独立复算与差异分析。选定关键数字可追溯，计算和任务交接可重放，所有无法勾稽项有解释，不填造缺失值 |
| **v0.4 单公司投资案例与团队复核** | 在明确假设下，团队能否形成一致、可复算的价值判断？ | 业务/假设、财务、估值任务与依赖；Watch 计划；情景与价格时点；市场隐含预期；Reviewer 质疑与整合；手动触发团队复核，保留 single 对照 | **R4-A** 投资案例、假设及 Watch 计划；**R4-B** 情景计算与版本化领域交接；**R4-C** 团队复核和敏感性验收。关键假设、计算与分歧处置可核查；报告团队与 single 的质量/预算差异；缺价格/共识数据时明确限制 |
| **v0.5 持续 Watch / Review / Update** | 面对连续新输入，Analysis Team 能否及时、可靠地维护投资判断？ | 固定初始案例及连续信息流；事件触发和到期完整复核；假设与模型影响分析；增量更新；无变化/资料不足/证据撤回；任务恢复；基线与相关资料并发检查；注意力事件 | **R5-A** Watch 计划、来源覆盖及事件批次；**R5-B** 团队 Review 与模型/建议修订；**R5-C** 采纳、并发冲突、恢复及序列回放。重大遗漏、误触发、复核滞后、修订正确性和下游过时使用可计量，旧结果不能被标为已覆盖新资料 |
| **v0.6 公司发现、多公司迁移与资本比较** | 能否找到值得研究的公司，将方法迁移并比较机会？ | 在预先固定范围内试用 Discovery，记录候选依据与遗漏抽查；迁移验证使用事先登记的 3–5 家不同业务公司；比较预期回报、下行风险与共同暴露；记录不投资理由；接入只读持仓快照 | **R6-A** 发现任务与筛选评价；**R6-B** 未用于调优的迁移样本及逐公司质量/成本；**R6-C** 同时点机会比较。发现质量与研究质量分别报告，失败与排除公司保留，不以总体平均掩盖差异 |
| **v0.7 组合、资金与风险** | 怎样将多家公司研究转换成符合投资风格和约束的目标组合？ | 投资比例/现金/集中度策略；持仓、资金及未完成订单快照；目标仓位；机会替换与交易成本；独立风险检查；不可行原因 | **R7-A** 策略与账户契约；**R7-B** 目标组合及资金计划；**R7-C** 风险与提案回放。资金守恒，违反硬约束的提案被阻断，历史验证只使用当时可得信息，偏满仓不自动覆盖限额 |
| **v0.8 模拟交易闭环** | 经研究和风控的计划能否可靠转换成可对账的订单与成交？ | 执行计划与授权契约；模拟账户适配；幂等；部分成交/拒单/撤单；状态不明时查询；费用与现金/持仓账本 | **R8-A** 订单状态契约；**R8-B** 模拟端到端执行与对账；**R8-C** 故障及恢复演练。重复请求不重复成交，账实一致，陈旧计划不能继续执行；不将模拟成交效果等同实盘 |
| **v0.9 受控真实执行** | 在明确授权和资金边界下，真实账户能否可靠执行并恢复？ | 确定账户、资金及订单限额；最小权限；执行前时效与风险重查；停用控制；真实成交、费用及持仓对账；有限范围试运行 | **R9-A** 账户与授权验收；**R9-B** 限定范围真实闭环；**R9-C** 对账与异常处置验收。实盘以届时明确授权为前提；模拟通过不授予实盘权限；审计、恢复及现金边界在真实下单前具备 |
| **v1.0 小团队可靠运行** | 多位研究者能否长期、可追责地使用同一投资系统？ | 研究者、审核者与执行权限；共享持久化；跨任务恢复；备份还原；模型/数据升级管理；运营观测；实际团队试运行 | **R1-A** 协作和责任边界；**R1-B** 故障恢复演练；**R1-C** 持续试运行。权限隔离、审计可追溯、预算控制和恢复指标达到预先约定要求；由真实使用者验收 |

v0.3 开始建立持续研究状态与团队任务边界，v0.4 验证领域协作和手动复核，v0.5 验收持续自动触发及更新。Watch 是跟踪机制，与 WATCH 投资建议无关；没有新数据、检查失败和经复核无变化分别记录。团队 Reviewer 不替代外部评测或人的采纳。v0.4 的估值方法按业务特征选择，不要求所有公司都套同一种 DCF。v0.6 的对照公司在调优前登记；提前看过的数据应说明暴露情况。

本次补充 v0.6 的公司挖掘和 v0.7–v0.9 的组合、风险与交易方向，均属远期提案；v0.2 的十二项任务和验收门槛不变。业务流程先发现公司，实现顺序先验证研究方法，再检验发现是否有用。Discovery 的筛选样本与研究迁移的留出样本分别登记，不能只拿筛选出的成功案例证明迁移能力。

影响账户安全、资金正确性和恢复的基础能力随交易阶段前置，不能等到 v1.0 才补。首页的简洁卡片方向随真实事件任务验证，阅读与业务决定保持独立。

各远期版本在启动时冻结自己的来源、任务、成功标准和成本上限。发现前序基础不足时，优先修正前序成果；如果需要调整版本顺序，保留原因和证据。

## 5. 架构随能力演进

| 边界 | 持续承担的责任 | 首次重点收敛 |

| 公司发现 | 投资范围、筛选依据、研究优先级、候选和排除记录 | v0.6 限定范围试用；数据能力复用研究数据入口 |
| 研究数据 | 来源获取、时点、固定索引、事实、指标、证据与缺口 | v0.2 限定当前来源接口；v0.3 统一跨期与重述口径 |

| 持续 Watch / Review / Update | 跟踪计划、事件相关性、到期复核、影响传导、增量修订及覆盖状态 | v0.3–v0.4 显式记录与手动验证；v0.5 连续信息流和周期复核验收 |

| 组合与资金 | 从研究建议、账户快照和策略形成目标仓位及现金计划 | v0.6 只读快照；v0.7 可复放提案 |
| 独立风险检查 | 现有/目标组合风险、硬约束、拟议交易检查及失效条件 | v0.7 起；规则检查与情景分析分别验收 |
| 执行与账户账本 | 获授权计划、订单、成交、费用、资金和持仓对账 | v0.8 模拟；v0.9 明确授权后的受控真实执行 |
| 评测与实验 | 参考数据、错误分类、研究复核、实验比较 | v0.2 起独立维护；不得成为 Agent 执行输入 |

这是一张职责图，不要求为每项创建服务或目录。六类业务角色及分析内部的领域任务见 [职责提案](AGENT_SYSTEM_DESIGN.zh-CN.md)。架构必须能承载 Analysis Team；具体团队组织以固定任务上的质量、成本和人工负担选择，single 作为同一契约下的基线或单成员配置。持续研究状态独立于模型会话保存。既有 `agents` 中的存储、预算与资料读取仅在当版修改触及边界时逐步迁移。

## 6. 每版如何验收

所有版本同时交付：**版本任务书、可重放产物、评价结果、人工结论、剩余缺口与下一步决定**。

| 层次 | 评价内容 | 证据与责任 |
| --- | --- | --- |
| 工程正确性 | 来源身份、文件完整性、计算、版本/权限边界、失败处理、可重放性 | 自动检查与具体日志；由执行者记录，复核者复现 |
| 研究质量 | 重要遗漏、事实支持、口径、因果解释、未知与反证、有用性 | 明确 rubric、逐项处置与真实研究者复核；模型可协助提出意见，不能代签 |
| 使用效果与成本 | 完成研究任务的耗时、返工、重大错误、调用成本、复核负担 | 固定任务前后对照，任务规模与人工耗时分别记录；没有对照就写未测量 |
| 长期投资反馈 | 原假设如何兑现，预测误差、估值变化和投资结果的关系 | 使用当时冻结的信息与决定做复盘；持续积累，不以一两个季度的收益作软件发布门槛 |

判定规则：

- **通过**：当版必需产物齐全，硬性检查通过，人工研究验收有真实记录。
- **未通过/待补**：仍有阻断项、未完成人工复核，或缺少能验证结论的证据。
- **待观察**：必须经过时间才能评价的投资假设单独保留；不能冒充已兑现，也不阻塞与之独立的软件交付。
- 研究参考答案发现错误时创建新版本，重新对所有对照产物评分；禁止只修对己有利的一边。
- baseline 分数低不妨碍“建立了可信评测基线”的版本验收。质量不足的能力继续标为实验性，不能升级为已可靠自动化。

## 7. 执行节奏

每个 todo 都有 ID、依赖、负责人、交付物和完成证据。执行者负责实现与记录，项目负责人负责业务范围、人工研究复核及最终签收。只有一个人复核时如实记录，不声称独立双人审核。

每周一次短复盘，或在一个里程碑完成时复盘：本周期产生了什么证据；主要错误或阻塞是什么；下一周期只推进哪个结果。时间是控制投入的约束，验收决定版本状态。

版本范围在首次运行前冻结。新想法进入后续 backlog；当版只插入影响正确性、数据保全或当前里程碑交付的必要任务。每版结束更新本路线图，并保留范围变化原因。
